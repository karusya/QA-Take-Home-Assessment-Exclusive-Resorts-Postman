# Exploratory Test Report — Exclusive Resorts Inquiry Form

**Target:** https://public-site.stage.exclusiveresorts.com/inquire/
**Date:** 2026-09-15
**Method:** ~45 min manual exploratory session (DevTools Network/Console + accessibility tree open throughout), a handful of real form submissions using clearly-fake data (`QA Candidate` / `Karina Zhdanova`, `karina.zhd+test@gmail.com`, `303-555-0100` — a NANP-reserved fictional number).

## Findings

| ID | Title | Severity | Steps | Expected | Actual |
|---|---|---|---|---|---|
| BUG-01 | Email validation race condition shows stale "invalid" error on a valid address | High | 1. Focus Email. 2. Type a multi-segment address, e.g. `qa.candidate.assessment+test@gmail.com`, retype/correct a character mid-way, then tab out. 3. Watch DevTools → Network for `POST /validate-email/`. | The error message reflects only the current field value; a valid address shows no error. | `POST /validate-email/` fires on effectively every keystroke with no debounce and no cancellation of in-flight requests — a single field edit produced **4 overlapping requests within ~50ms**. If an earlier request's `{"valid":false}` response resolves after a later `{"valid":true}` one, the UI is left showing "Email is not valid." for an address that *is* valid. Reproduced repeatedly; not tied to any one domain or character (confirmed both `gmail.com` and a portfolio domain pass in isolation but fail when typed quickly alongside other edits). |
| BUG-02 | "Last" name field has no accessible name | Medium | Inspect the DOM: `<label for="input_0">Name*</label>` sits above two inputs (First, Last). | Every form control has a programmatically associated label (WCAG 4.1.2 / 3.3.2). | The `for` attribute only points at the **First** input's id. The **Last** input has no `<label>`, `aria-label`, or `aria-labelledby` at all — a screen reader announces it as an unnamed edit field. |
| BUG-03 | Phone field rejects valid numbers when the country selector doesn't match, contradicting its own helper text | Medium | 1. Load the form from a non-US browser locale. 2. Type a plain 10-digit US number (e.g. `3035550100`) into Phone without touching the country flag selector. 3. Tab out. | Per the field's own copy — "Numbers only, please. You may include a + for international codes." — a digit string should be accepted. | The field is a `vue-tel-input` widget that validates against whatever country is pre-selected (defaults from browser/IP locale — in our session it defaulted to Portugal). A fully valid, complete number for a *different* country is rejected with "Please enter a valid phone number" unless the user also manually changes the flag — a step the visible instructions never mention. |
| BUG-04 | Custom "Preferred Time of Day" / "Preferred Days" dropdowns have no ARIA semantics | Medium | Inspect the DOM of either dropdown's trigger and option list. | Interactive custom widgets expose `role="combobox"`/`"listbox"`/`"option"` and `aria-expanded` per the WAI-ARIA Authoring Practices. | Every node is a bare `<div>` — no `role`, no `aria-expanded`, no `aria-haspopup`; only the outer wrapper carries a stray `tabindex="0"`. A screen-reader user gets no indication these are interactive controls, and tooling that inspects the accessibility tree (axe, Playwright's `getByRole`) cannot address them semantically. |
| BUG-05 | Honeypot field's resilience against autofill/assistive tech is unverified | Low / informational | Inspect the DOM: a text input named `MessagingPreferences` (`id="hp-field"`, placeholder `"Can we message you?*"`) sits among the real fields, presumably as a bot trap. | A honeypot field should be unreachable by real users under every input method (tab order, screen reader, browser autofill, password-manager autofill) so it never gets accidentally populated. | Not confirmed either way in this pass — flagging because if any autofill heuristic (browser or password manager) matches on the visible `Can we message you?*` placeholder and fills it, that legitimate submission would likely be silently dropped as bot traffic. Worth a dedicated check (tab-order position, `aria-hidden`, and an autofill test in a couple of browsers) before relying on it in production. |
| BUG-06 | Consent is enforced only client-side — the raw API creates a real CRM lead with no consent flag at all | **Critical** | 1. Open DevTools → Network, capture the shape of a real `POST /submit-form/` request. 2. Send that same request directly (bypassing the UI) with the `termsAgreement`/consent key removed from the `values` payload entirely. 3. Inspect the response. | The server should independently enforce the consent requirement (a real legal/compliance requirement per the assignment brief) and reject the request with a 4xx error, exactly like a required-field validation failure. | The request succeeded with `200 OK` and `{"data":{"id":126850345}}` — a real lead was created in the CRM with no consent recorded anywhere in the payload. The UI-level block (BUG list item confirmed below) is the *only* thing stopping a non-consenting submission; anyone who can POST directly to the endpoint (or replay/modify a request) bypasses consent entirely. This is a genuine compliance exposure, not just a UX gap. |
| BUG-07 | Missing a required field returns a raw 502, not a validation error | High | `POST /submit-form/` with the `values` payload missing a required key (e.g. no `Email`). | A 4xx response with a field-level validation error, so a legitimate integration (or a retrying client) can tell "you sent bad data" from "the server is down." | The endpoint returned `502 Bad Gateway` with no JSON body — indistinguishable from an infrastructure outage. Whatever validation exists appears to run after something that throws unhandled on a missing key, rather than short-circuiting with a clean 4xx. |
| BUG-08 | Malformed email in the submit payload also returns 502 instead of a validation error | High | `POST /submit-form/` with `Email` set to a clearly malformed value (e.g. `not-an-email`). | A 4xx validation error naming the offending field, consistent with what `/validate-email/` itself reports. | Same failure mode as BUG-07: `502 Bad Gateway`, no body. The client-side `/validate-email/` check is the only thing standing between a malformed address and this crash — anyone posting directly to `/submit-form/` skips it entirely. |
| BUG-09 | `GET` on the submit endpoint returns 502 instead of 405 | Medium/High | `GET /submit-form/` (no body). | `405 Method Not Allowed`, per standard REST semantics and the assignment's own expected behavior (API-06). | `502 Bad Gateway`. Combined with BUG-07/08, this suggests the backend (or a fronting proxy/serverless function) is crashing rather than validating on anything outside the exact happy-path shape the SPA sends — worth a dedicated look from the backend team, since a 502 on cheap, obviously-malformed traffic is also a minor DoS/cost-amplification concern. |
| BUG-10 | Inconsistent vertical spacing in the "Filter by Category" list — large gap between "Travel" and "Sports & Leisure" | Low | 1. On a mobile viewport (iOS Safari, ~402×874), open the site's "Filter by Category" panel. 2. Visually inspect the spacing between each category option, top to bottom. | Every category option is spaced evenly (~60px apart), consistent with the rest of the list's rhythm and the site's design system. | The gap between "Travel" and "Sports & Leisure" is visibly larger than every other gap in the list (~25% wider) — reads as a layout/CSS spacing bug (an extra margin, or a hidden/collapsed element between the two options), not an intentional grouping. **Found outside `/inquire/`, while exploring the broader site** — see note below. |
| BUG-11 | "Filter by Category" panel doesn't lock background scroll on mobile | Medium | 1. On a mobile viewport (iOS Safari), open the "Filter by Category" panel. 2. Try to scroll within the panel itself (e.g. to check for more categories below "Fashion"). 3. Observe what actually moves. | Scrolling while the panel is open scrolls only the panel's own content; the page underneath stays locked in place, per standard modal/overlay behavior. | Confirmed via screen recording: the scroll gesture scrolls the page *behind* the overlay instead of the category list itself — disorienting, since the visible, interactive surface is the panel, not the page behind it. **Found outside `/inquire/`, while exploring the broader site** — see note below. |

**Note on BUG-10/11:** both were found on the site's mobile "Filter by Category" panel, outside the `/inquire/` inquiry form this assessment is scoped to. Included anyway since they're real, reproducible findings from the same staging environment — flagging the scope so it's clear they're a bonus, not part of the core deliverable.

## What was tried and didn't turn up a bug

- **UI-level** consent enforcement works correctly — confirmed via Network tab that `POST /submit-form/` is never sent from the form itself while `termsAgreement` is unchecked. **However, see BUG-06:** this is not backed up server-side — a direct API call with no consent field at all is accepted and creates a real lead. Treat the client-side block as UX only, not as the compliance control.
- XSS payloads (`<script>…</script>`) in Name render as inert text; no script execution observed.
- SMS opt-in is genuinely optional — submission succeeds with it unchecked.
- Postal code accepted both a US 5-digit value and would reasonably be expected to accept international formats (not exhaustively fuzzed in this pass — see test plan TC-09 for the case that should extend this).
- Mobile viewport (375px) renders the form usably; no layout breakage observed at that width.

## Notes for the automation suite

- `POST /validate-email/` and `POST /submit-form/` are the two backend calls involved; the Playwright suite stubs both by default (see `playwright/fixtures/inquiry.fixtures.ts`) so CI never creates a real CRM lead or gets tripped up by BUG-01's flakiness.
- The DOM also contains a second, initially-hidden "Share a Referral or Club Connection" form (and a meeting-scheduler form) that only render after a successful submit — both also have their own "Submit" button, so any locator for "the" submit button must be scoped to the first form on the page.
- BUG-06/07/08/09 were found via direct calls to `/submit-form/` (bypassing the UI), captured in the Postman collection (`postman/collection.json`) as API-02, API-03, API-04, API-06. The corresponding SQL-injection check (API-05) was **not** run live against production in this pass — see the Postman collection's README notes for why and what I'd do instead.
